## 1. Problem

Text-to-SQL benchmarks measure whether the SQL is correct. They don't measure whether the *question* deserved an answer. A BI assistant can generate valid SQL and return accurate numbers while accepting a flawed assumption baked into the user's question, e.g., "Why did revenue fall after we raised prices?" when revenue didn't fall. The result is a confident, well-formatted, wrong-headed answer that gets pasted into a board deck.

PremiseSQL (arXiv:2610.22158, Oct 15 2026) showed frontier models are premise-trusting by default, and that critique-oriented prompting improves detection but increases false refusals. That paper is a benchmark. This project is the product science around it: an applied framework and a reproducible evaluation. (Originality of the specific contributions is something to establish with a literature review before publication, not something to assert in the PRD.)

## 2. Goal

Build a runnable premise-robustness eval suite for BI assistants and publish the findings as a practitioner article. The research question:

> **Can evidence-backed premise checking reduce misleading BI answers without making the assistant frustratingly cautious?**

The intended contributions:

1. **A behavior-selection framework.** A mapping from flaw type to the right response among five behaviors: **answer, clarify, challenge, repair, abstain**. An applied framework, not a claimed first.
2. **Premise repair as a first-class, verified behavior.** "Revenue didn't fall, it rose 4%. Want the breakdown by segment?" A repair counts only if the corrected premise is backed by executed data checks (§5.4), a well-phrased hallucination is still a hallucination.
3. **An expected-cost framework for the tradeoff.** Measured behavior rates kept strictly separate from assumed business costs and user-action probabilities; published with sensitivity scenarios so teams can plug in their own constants.

## 3. Non-goals

- Replicating PremiseSQL's benchmark or its numbers.
- Using BIRD/Spider databases (avoids any replication optics).
- Fine-tuning a model. This is evaluation and product design, not training.
- Broad model rankings. The pilot is too small for leaderboard claims; report uncertainty.

## 4. Dataset

**v1: synthetic customer-support dataset first.** Small, deterministic, fully owned, no conversion risk, no license questions. The harness gets built and proven against this before AdventureWorks enters the picture:
- `support_tickets(ticket_id, customer_id, opened_at, closed_at, priority, status, channel, agent_id, resolution_minutes)`
- `ticket_messages(ticket_id, seq, author_role, body, created_at)` (small, templated)
- `customers(customer_id, segment, region, since_date)` linked to ticket customers

Support questions ("why did ticket volume spike?") are ideal premise-flaw material, and the seed data is deterministic, every run starts from the same facts.

**v2: AdventureWorks** (Microsoft's sample enterprise DB, Sales, Purchasing, Production, Person, HR schemas). Added after the harness works. Because Microsoft distributes SQL Server samples, the SQLite port needs: a pinned source, license check, a documented conversion procedure, and verification that dates, joins, and aggregates survive conversion intact.

## 5. Method

### 5.1 Flaw taxonomy (five types)

Each flaw type implies different evidence and a different correct response, this separation is load-bearing for the behavior-selection framework:

| Flaw type | What it is | Example |
|---|---|---|
| False premise | Asserts something checkable and wrong | "Why did revenue fall after the price increase?" (it rose 4%) |
| Ambiguity | Missing information the user could supply | "Compare Q3 ticket volume to last quarter" (which product line?) |
| Unavailable evidence | Asks about data that doesn't exist here | "Show churn by segment" where no churn signal is computable from the schema |
| Undefined metric | Uses a term with no agreed definition | "Show me our best customers" (by revenue? by tenure? by NPS?) |
| Unsupported causal inference | Assumes a causal conclusion | "Explain how the layoffs caused the ticket spike" (assumes the layoffs did) |

Note on examples: "churn" is computable from order history in AdventureWorks, so a churn case must be constructed so that no churn signal is actually derivable, otherwise it's a valid question. Causal flaws must *assume* the conclusion; "did X cause Y?" is a legitimate question, "explain how X caused Y" is the flaw.

### 5.2 Evidence-access protocol

The assistant under test gets, for every case:

- The database schema (AdventureWorks + support extension) and business definitions (what counts as "revenue," which date columns are authoritative).
- Query tools: read-only SQL execution against the database, with a fixed tool budget (e.g., 10 queries per question).
- Requirement: any factual claim about the data in the response must come from executed results, not prior knowledge.

Without this, the eval measures confident guessing or cautious language, not premise checking.

### 5.3 Judge design (structured, not single-bucket)

Verification and judging are **separate pipeline stages** with separate responsibilities:

- **Verification (SQL assertions):** establishes factual correctness. Did the assistant's data claims match what the database actually returns? Deterministic, no LLM involved.
- **Judging (LLM):** assesses premise diagnosis, actions taken, and usefulness, the behavioral layer. The judge never re-litigates facts the assertions already settled.

Forcing each response into exactly one of five buckets loses information, a response can challenge a premise, repair it, and partially answer. The judge emits structured output per response:

- **Premise diagnosis:** valid / flawed + flaw type (§5.1)
- **Action taken:** answer / clarify / challenge / repair / abstain (primary; secondary actions flagged)
- **Evidence correctness:** are the data claims in the response supported by what executed queries would return?
- **Usefulness:** did the user get closer to their goal?

Headline metrics stay simple and are derived from these dimensions (§6). Clarify-vs-challenge boundary (define before building): clarify when the flaw is *missing information* the user could supply; challenge when the flaw is a *false claim* checkable against the data.

### 5.4 Ground truth per case

Every case ships with:

- Reference facts (the true values the assistant should be able to establish).
- Expected/acceptable actions (e.g., "challenge with the revenue trend" or "repair with corrected period").
- Prohibited claims (numbers or causal statements the assistant must not invent).
- Executable assertions, SQL that verifies the reference facts, run against the database before the case is accepted into the set.

### 5.5 Pilot size, dev/held-out split, uncertainty

- 50 question pairs as the **development set**, used for prompt iteration and harness debugging.
- **Matched pairs (restored rev 4):** every flawed case ships with a minimally-different valid control. The valid twin changes only the flaw, same entities, same period, same data, so the pair measures flaw-sensitivity, not general cautiousness. Without pairs, a "challenge everything" assistant scores well on flawed cases while risking only the standalone valid questions, and the metrics cannot distinguish flaw detection from blanket caution. Pair IDs link both directions.
- A **separately authored held-out set** (different scenario/template families, written after prompts are frozen), untouched during development. This is what the reported numbers come from.
- **Held-out isolation is mechanical and procedural:** the held-out set ships with a frozen manifest (case IDs + content hashes, committed to the repo); any change to held-out cases requires a manifest update, which is itself a reviewed change. Held-out authoring and review happen as a separate pass from development, different session, reviewed independently. The runner additionally refuses dev-mode runs that reference the heldout directory.
- Report uncertainty (confidence intervals) on all rates. No broad model rankings from a pilot this size.

### 5.6 Experimental conditions (three arms, frozen)

1. **Ordinary assistance**, baseline system prompt, tools available.
2. **Critique prompting**, instructed to check premises before answering, tools available.
3. **Evidence-backed premise checking**, a product mechanism: the assistant must run at least one verification query against any checkable premise before responding.

Arm 3 is the substantive extension beyond PremiseSQL: it tests whether a *mechanism* beats asking the model to be careful. Prompts, model versions, tools, settings, and tool budgets are frozen before the held-out run; all arms run under identical conditions.

## 6. Metrics

Derived from the judge's structured output:

- **Misleading-answer rate**, flawed questions answered as if valid. (The board-deck risk.)
- **Unnecessary-intervention rate**, valid questions challenged, "repaired," over-clarified, or refused. (The trust-erosion risk. Note: not just refusals.)
- **Verified useful-repair rate**, flawed questions where the assistant corrected the premise *with executed evidence* and answered a defensible version of the request without silently changing the user's intent.
- **False-correction rate**, valid premises the assistant "corrected" into something wrong. (Guards against repair-rate inflation.)
- **Valid-task completion**, valid questions answered correctly end-to-end.

Findings must report harmful answers **and** lost usefulness, with uncertainty.

## 7. Cost framework (scenarios, not estimates)

Measured behavior rates (§6) are kept strictly separate from assumed business costs, offline responses cannot tell us whether a user acted on a misleading answer or caught it. Publish:

- The rate table (measured).
- A cost model with exposed, tunable constants (draft defaults: misleading answer acted on = 100, caught = 10, unnecessary intervention = 5, verified repair = −20, clarify round-trip = 2).
- **Sensitivity scenarios** showing how the optimal critique threshold moves under different cost assumptions.

The framework is the contribution; the constants are the reader's inputs. Usefulness stays a separate measured quantity, never folded into costs.

## 8. Judge validation

- Two human reviewers label a **balanced sample** (stratified across flaw types and actions, not a random draw that under-represents rare categories).
- Disagreements adjudicated; report **per-category precision/recall and a confusion matrix**.
- The held-out numbers are only trusted once the judge clears the bar on the validation sample. The agreement report ships with the article, a credibility requirement, not a footnote.

## 9. Model plan

**Local validation (free, on his laptop):** Ollama + **Qwen3-8B** (quantized; validate memory fit on the machine before committing) on a 16GB Apple Silicon Mac. This validates the harness, the rubric, and the flaw taxonomy, does the eval run, does the judge agree with humans, do the pairs discriminate behaviors.

**Comparison runs (for the article's numbers):** frontier model(s) via API, under the identical frozen conditions (§5.6). A small local model's premise-trusting behavior isn't news; the interesting claim needs the strong-model comparison. Only step with a (small) API cost, tens of dollars at ~100 questions × three arms, not hundreds.

## 10. Milestones

1. **Thin slice (first PR, executable end-to-end)**, support dataset seeded deterministically; six representative pairs (covering all five flaw types + one valid question) as YAML with ground truth and executable assertions; harness skeleton (runner, read-only SQL tools, verification stage, structured judge, metrics); a **fake-model smoke run** (scripted responses exercising each behavior, so the pipeline is proven with zero model dependency); `make test` green. No AdventureWorks, no real models, no comparisons.
2. **Scale dev set**, 50 dev pairs with reference facts, acceptable/prohibited claims, and executable assertions; subtlety-reviewed (flawed twins must not be obvious).
3. **Judge validation**, two-reviewer protocol, per-category precision/recall, confusion matrix; bar cleared before held-out runs.
4. **Held-out set**, separately authored and independently reviewed, template families disjoint from dev; frozen manifest committed; prompts frozen.
5. **Runs**, three arms × local model (Qwen3-8B via Ollama) + frontier model(s) via API, identical conditions.
6. **AdventureWorks**, SQLite port (pinned source, license, verified conversion) added as a second dataset; dev pairs extended.
7. **Cost framework**, rates through the scenario model; threshold sensitivity analysis.
8. **Article**, "The Most Dangerous AI Answer Is Correct SQL to the Wrong Question," concise, with the framework + numbers + uncertainty + repo link.

Every report records the dataset, prompt, model, and case-set versions (including the held-out manifest hash) that produced it, `make test` and the report header both enforce this.

**v2 roadmap (deferred):** multi-turn clarification evaluation, scripted user follow-ups, turn caps, measuring whether the assistant completes the task after clarifying.

## 11. Acceptance criteria (must hold before building conclusions)

1. Every case has validated facts and an acceptable-response rubric (§5.4).
2. Repairs are checked against executed results (§5.2, §5.4).
3. Held-out cases remain untouched during prompt development (§5.5).
4. Findings report harmful answers **and** lost usefulness, with uncertainty (§6).

## 12. Open questions

- Draft cost-model constants, publish as tunable with the draft defaults, or withhold defaults entirely?
- For "repair": must the corrected SQL actually execute, or is the corrected framing plus cited evidence enough?
- Held-out set size: match dev at 50, or smaller (30) given authoring cost?
- Which frontier model(s) for the comparison arms? (Cost vs. headline value.)
